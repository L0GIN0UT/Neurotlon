# Поиск датчиков: мост ↔ лаунчер

Версия 1. Схема сообщений — [`sensor-discovery.schema.json`](sensor-discovery.schema.json). Это отдельный контракт от [`bridge-protocol.md`](bridge-protocol.md) (мост → игра): тот не меняется.

Нужен экрану настройки стенда: живой список датчиков рядом, подключение выбранного и опознание «чей это датчик». Bluetooth держит мост (`neurotlon-bridge --discover`), лаунчер NeuroSDK не загружает.

## Транспорт

- Лаунчер запускает `neurotlon-bridge --discover` и общается через stdin и stdout, по одному JSON-объекту в строке (JSONL, UTF-8).
- Каждое сообщение моста — строка с меткой `NEUROTLON_DISCOVERY=`, дальше JSON. NeuroSDK пишет свой мусор в тот же stdout (иногда без перевода строки), поэтому получатель ищет метку в строке, разбирает JSON после неё, а строки без метки, не JSON, не проходящие схему или с неизвестным `type` отбрасывает.
- Пункт `devices`, сообщение `link` и все команды строгие: лишнее поле делает их неверными. В `devices` не больше 64 пунктов, имя и серийный номер до 128 знаков, адрес и `id` до 64, без управляющих, суррогатных и форматирующих знаков (мост их вычищает, слабые по RSSI лишние устройства не показывает); `age_ms` не больше 3 600 000. Один пункт, не прошедший схему, получатель отбрасывает сам, остальные берёт; числа `NaN` и `Infinity` недопустимы.
- Строки лаунчера (stdin моста) — JSON без метки. Нехорошая, неизвестная по схеме или неподходящая строка отбрасывается мостом.
- Закрытие stdin (как и `quit`) означает «освободить датчики и выйти». Процесс должен быть привязан к процессу лаунчера (Job Object «убить при закрытии»), чтобы не остаться сиротой.
- Мост запускается один; рабочий мост (`neurotlon-bridge --profile ...`) одновременно не работает: оба держат Bluetooth.
- Для разработки и проверки интерфейса без железа: `neurotlon-bridge --discover --fake` (устройства появляются и исчезают по сценарию).

## Мост → лаунчер

- `hello` — сразу после запуска: `{"type":"hello","v":1}`. Версия несовместимых изменений — новое `v`.
- `devices` — список найденных устройств: `scanning` (идёт ли поиск) и `items`. Шлётся только при изменении (устройство появилось или пропало, сменилось имя, серийный номер, вид или признак «в эфире», `scanning`; RSSI считается изменением при сдвиге не меньше 5 дБ) и не чаще двух раз в секунду. Порядок элементов: по времени первого обнаружения, он не меняется от RSSI.
  - `id` — идентификатор устройства в командах; равен `address`. Адрес уникален даже у двух Callibri с одним именем;
  - `kind` — `brainbit` или `callibri` (Kolibri считается Callibri);
  - `name` — имя из эфира;
  - `serial` — серийный номер; у Callibri в эфире пустой, номер сообщается после подключения (поле `link.serial`) и после этого заполняется и здесь;
  - `rssi` — уровень сигнала в дБм, `null`, если неизвестен;
  - `age_ms` — сколько миллисекунд устройство не видно, на момент отправки сообщения. Мост шлёт `devices` в момент, когда устройство вышло из эфира (`age_ms` перешёл 15 с) или вернулось, а между сообщениями `age_ms` у устройства в эфире не обновляется. Поэтому получатель считает устройство «в эфире», пока `age_ms` меньше 15 с; у вышедшего из эфира прибавляет к `age_ms` время, прошедшее с получения («нет в эфире 20 с»). Вышедшее из эфира остаётся в списке. Пока поиск выключен или стоит на паузе (идёт подключение), список не стареет: он замирает как есть. Без соединения устройство, не видимое дольше 60 с, из списка убирается. Подключённое устройство всегда в эфире.
- `link` — состояние подключения к устройству (после `connect`); шлётся при смене состояния, серийного номера, заряда, контакта, `signal` и заметном сдвиге `level` (не чаще 5 раз в секунду):
  - `state` — `connecting`, `connected`, `failed` (причина в `error`, по-русски), `lost` (связь пропала; вернётся в `connected`, если устройство вернулось);
  - `serial` — серийный номер, прочитанный после подключения, пустой до него;
  - `battery` — заряд, %, `null`, если неизвестен;
  - `contact` — контакт электродов Callibri (`true` — норма), `null` — датчик не сообщает;
  - `signal` — отсчёты приходят (последние получены не раньше 2 с назад);
  - `level` — грубый уровень сигнала 0…1 для опознания мышцы («напрягите мышцу с датчиком: полоска должна расти»), только у Callibri; не годится для игры: сырая RMS без калибровки, `null` у BrainBit и пока нет отсчётов;
  - `error` — только у `failed`.
- `error` — ошибка моста, по-русски и понятно оператору (например, Bluetooth выключен). Поиск при этом остановлен.

## Лаунчер → мост

- `scan` — `on: true` включить поиск, `false` остановить (найденные остаются в списке, подключения не трогаются). Устройства появляются в `devices` каждые 0,5 с по мере нахождения.
- `connect` — подключиться к устройству `id` вида `kind` и держать соединение: Callibri переводится в режим ЭМГ, запускается сигнал. На время подключения поиск ставится на паузу и затем возобновляется, если был включён. Подключения идут по одному, не дольше 20 с.
- `release` — отпустить устройство `id` (датчик освобождается для других программ и для рабочего моста).
- `quit` — отпустить всё и выйти.

## Файл `bridge.toml`: назначение датчиков

Тот же мост читает в `[devices]` два вида записи (вид определяется типом значения):

```toml
[devices]
eeg = "BB-100200"        # старый вид: только серийный номер

[devices.emg_left]       # новый вид: пишет экран настройки
address = "D8:AA:00:00:00:02"   # главный ключ
serial = "CA-204816"            # запасной, если адрес сменился (из пробного подключения)
name = "Callibri_Red"
kind = "callibri"
```

Ключи роли: `eeg`, `emg`, `emg_left`, `emg_right`; вид датчика роли: `eeg` — `brainbit`, остальные — `callibri`. Роль ищет датчик по адресу, а если по нему не нашла, по серийному номеру. Один датчик в двух ролях нельзя (одинаковый адрес или серийный номер). Читает и пишет файл общий код `neurotlon_contracts.sensor_devices`; писать новый вид, старый только читать.
