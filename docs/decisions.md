# Принятые решения

Короткий журнал решений, которые отличаются от ТЗ v1.0.0 или уточняют его.

| # | Решение | Вместо (ТЗ) | Почему |
|---|---|---|---|
| 1 | Два независимых проекта: сайт (отдельный репозиторий, на паузе) и система в зале (этот монорепозиторий) | Обмен данными Сайт ↔ Система | Связывать VDS и локальную сеть избыточно; итоговая таблица выкладывается на сайт вручную |
| 2 | Система работает только в локальной сети зала: ПК админа = сервер | Локальный сервер + синхронизация с сайтом | Нет зависимости от интернета |
| 3 | 3 стенда: дартс, футбол, понг | 4 BCI-места | Понг — один ПК с двумя Callibri |
| 4 | Модальности: дартс и футбол — ЭЭГ + ЭМГ, понг — только ЭМГ | Поле `modality` с одним значением | По концепции 4.0.0; поле — список |
| 5 | Участник = заранее созданный ID (20 шт., `NT01…NT20`), имя для табло — необязательно | Анкета с ФИО и медданными | Персональных данных в базе нет |
| 6 | QR — источник истины; после скана окно «Это я», запасной путь — ручной ввод ID | Назначение участника диспетчером | Админ не успевает назначать вручную |
| 7 | На стендах — вебка, на планшетах — камера в браузере (HTTPS, локальный сертификат) | — | Без докупки сканеров |
| 8 | Бейджи печатаются до мероприятия: только ID и QR; команда видна на экранах | Бейдж с цветом команды после жеребьёвки | Нет печати в день мероприятия |
| 9 | Результат подтверждает волонтёр; статусы: введён → подтверждён → заблокирован | введён → предварительный → подтверждён судьёй → заблокирован | Судья только разбирает запросы на исправление |
| 10 | Волонтёры: 3 аккаунта (дартс, футбол, понг) с логином и паролем, создаёт суперпользователь, вход на планшетах заранее | PIN-коды | — |
| 11 | База — SQLite (WAL) через SQLAlchemy + Alembic | PostgreSQL | Масштаб 20 участников; ноль администрирования; переход на PostgreSQL — смена строки подключения |
| 12 | Игры — pygame-ce; BCI-мост — отдельный процесс на стенде | — | Один язык со всем стеком; игры не зависят от SDK датчиков |
| 13 | Итоги и рейтинг не хранятся — вычисляются из результатов секций | — | Исправление результата сразу пересчитывает всё |
| 14 | Методика подсчёта очков внутри игр — отдельный документ (в работе); шкалы в настройках | Конкретные цифры в ТЗ | Методика ещё не утверждена |
| 15 | Результат отправляется одним запросом на сессию (1–2 участника) с общим `session_id`; оба игрока матча понга — в одном запросе | Отдельное поле «матч» | Сессия и есть матч; идемпотентность на всю пару |
| 16 | Время игры на стенде и время физической дисциплины хранятся на сервере (по дисциплине); меняют админ и судья, применяется со следующей сессии | Фиксированное время в коде | Нужно менять по ходу дня без пересборки |
| 17 | Число команд всегда чётное; лишние — в резерв | Нечётное число команд — последняя из резерва вне зачёта (концепция) | Дуэли без участников вне зачёта |
| 18 | Размер команды m выбирает админ из вариантов, которые показывает система | — | Концепция оставляет выбор людям |
| 19 | Результат со стенда сразу «подтверждён» и виден на табло; исправляет судья | Подтверждение каждого результата | Очки считает игра, участник подтвердил «Это я» |

## Открытые вопросы

- Кто и когда переводит результаты в «заблокирован» (предложение: судья — «Зафиксировать итоги» в конце дня).
- Начислять ли очки за сам факт прохождения секции; как считать команду неполного состава.
- Нужен ли исход дуэли или дуэль — только единица расписания.
- Нужны ли в первой версии трансляция, оверлей OBS и бегущая строка.
