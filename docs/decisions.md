# Принятые решения

Короткий журнал решений, которые отличаются от ТЗ v1.0.0 или уточняют его.

| # | Решение | Вместо (ТЗ) | Почему |
|---|---|---|---|
| 1 | Два независимых проекта: сайт (отдельный репозиторий, на паузе) и система в зале (этот монорепозиторий) | Обмен данными Сайт ↔ Система | Связывать VDS и локальную сеть избыточно; итоговая таблица выкладывается на сайт вручную |
| 2 | Система работает только в локальной сети зала: ПК админа = сервер | Локальный сервер + синхронизация с сайтом | Нет зависимости от интернета |
| 3 | 3 стенда: дартс, футбол, понг | 4 BCI-места | Понг — один ПК с двумя Callibri |
| 4 | Модальности: дартс и футбол — ЭЭГ + ЭМГ, понг — только ЭМГ | Поле `modality` с одним значением | По концепции 4.0.0; поле — список |
| 5 | Участник = заранее созданный ID (20 шт., `NT01…NT20`), имя для табло — необязательно | Анкета с ФИО и медданными | Персональных данных в базе нет |
| 6 | QR — источник истины; после скана окно «Это я», запасной путь — ручной ввод ID | Назначение участника диспетчером | Админ не успевает назначать вручную |
| 7 | На стендах — вебка, на планшетах — камера в браузере (HTTPS, локальный сертификат) | — | Без докупки сканеров |
| 8 | Бейджи печатаются до мероприятия: только ID и QR; команда видна на экранах | Бейдж с цветом команды после жеребьёвки | Нет печати в день мероприятия |
| 9 | Результат подтверждает волонтёр; статусы: введён → подтверждён → заблокирован | введён → предварительный → подтверждён судьёй → заблокирован | Судья только разбирает запросы на исправление |
| 10 | Волонтёры: 3 аккаунта (дартс, футбол, понг) с логином и паролем, создаёт суперпользователь, вход на планшетах заранее | PIN-коды | — |
| 11 | База — SQLite (WAL) через SQLAlchemy + Alembic | PostgreSQL | Масштаб 20 участников; ноль администрирования; переход на PostgreSQL — смена строки подключения |
| 12 | Игры по умолчанию — pygame-ce (см. решение 21); BCI-мост — отдельный процесс на стенде | — | Один язык со всем стеком; игры не зависят от SDK датчиков |
| 13 | Итоги и рейтинг не хранятся — вычисляются из результатов секций | — | Исправление результата сразу пересчитывает всё |
| 14 | Методика подсчёта очков внутри игр — отдельный документ (в работе); шкалы в настройках | Конкретные цифры в ТЗ | Методика ещё не утверждена |
| 15 | Результат отправляется одним запросом на сессию (1–2 участника) с общим `session_id`; оба игрока матча понга — в одном запросе | Отдельное поле «матч» | Сессия и есть матч; идемпотентность на всю пару |
| 16 | Время игры на стенде и время физической дисциплины хранятся на сервере (по дисциплине); меняют админ и судья, применяется со следующей сессии | Фиксированное время в коде | Нужно менять по ходу дня без пересборки |
| 17 | Число команд всегда чётное; лишние — в резерв | Нечётное число команд — последняя из резерва вне зачёта (концепция) | Дуэли без участников вне зачёта |
| 18 | Размер команды m выбирает админ из вариантов, которые показывает система | — | Концепция оставляет выбор людям |
| 19 | Результат со стенда сразу «подтверждён» и виден на табло; исправляет судья | Подтверждение каждого результата | Очки считает игра, участник подтвердил «Это я» |
| 20 | Команд две (одна дуэль); предел задаётся настройкой `NEUROTLON_MAX_TEAMS` | Число команд по итогам регистрации | Так решили организаторы |
| 21 | Игра — любой исполняемый файл (pygame-ce, Unity и др.); лаунчер передаёт `launch.json` и читает `result.json`, сигнал игра берёт у моста по TCP | Игры только на pygame-ce | Часть игр может быть сделана на Unity |
| 22 | Итоги фиксирует судья или админ кнопкой «Зафиксировать итоги» (`POST /results/lock`): подтверждённые результаты становятся заблокированными; заблокированные правит только админ | Кто блокирует — открытый вопрос | Судья ведёт конец дня; правка после фиксации остаётся у админа (раздел 8 архитектуры) |
| 23 | ПК админа — Windows с Docker Desktop (WSL2); образы собираются заранее и переносятся `docker save`/`docker load`; база в томе Docker, бэкап раз в минуту отдельным сервисом на внешний диск; сертификат — mkcert | База в папке Windows, установка из интернета на месте | В зале нет интернета; WAL не работает на смонтированных папках Windows |
| 24 | Счёт дуэли на табло — победы в понге (1 матч = 1 очко); очки по дисциплинам и игроков — сумма физ + BCI; на табло по каждой дисциплине топ-5 игроков команды | Счёт дуэли — сумма очков | Так задумано владельцем; формула может смениться, поэтому `duel_score` — отдельная функция |
| 25 | Названия и цвета команд задаёт админ (по умолчанию «Красные» / «Синие») | Только «Команда N» | Команды для зрителей должны быть узнаваемы |
| 26 | Оверлей OBS — `/overlay` (прозрачный фон, `?view=score\|full`, `?scale=`) | Отдельная трансляция | Достаточно Browser source в OBS |
| 27 | Очки за секцию дартса и футбола (физ и BCI) — не больше лимита дисциплины, по умолчанию 10; понг — победы | Очки секции без верхней границы (до 1000) | Физические секции оцениваются по той же небольшой шкале, что и BCI; админ и волонтёры не могут ввести больше. Лимит — `discipline.max_section_points` (1…1000), меняют админ и судья; понг им не ограничен: его `points` — счёт игры, секция считается как победы × `win_points` |
| 28 | Очки — целые числа | Десятые доли (шаг 0,5) | Владелец: «десятые доли надо убрать». `points` — целое 0…1000 в API, играх (SDK, кит Unity, проверка), планшете, правке судьи, базе (миграция 0008 округляет старые значения), табло и XLSX; дробное — 422 `invalid_entries`. JSON-число вида `7.0` принимается как 7 |
| 29 | Понг: ракетка движется поперёк стола, положение задаёт сила ЭМГ (0…1 от края до края); счёт до 11; время вышло при разном счёте — побеждает ведущий, при равном — золотой мяч (следующее очко решает); подача меняется через 2 очка. Время на экране не показывается. Экран игроков разделён пополам: у каждого вид от первого лица из-за своего края стола (красный слева, синий справа); для зрителей отдельный вид с табло на стене (второй экран) | Вид сверху для игроков; цвета ракеток по цветам команд из лаунчера; один экран | Владелец. Игрокам удобнее видеть стол и свою ракетку «изнутри», а зрителям — арену и табло. Числа (скорость, зона отбития, 11 очков) — в `PongTuning`, методики очков для понга пока нет. Цвета команд в `launch.json` не передаются, менять контракт ради этого не стали |
| 30 | Дартс: вид от первого лица на настоящую мишень, 5 бросков. Сосредоточение (`eeg`) задаёт зону разброса: вокруг центра светлый «прожектор» (снаружи мишень затемнена), чем выше сосредоточение, тем он меньше; прицел гуляет внутри. Бросок — сжатие руки (`emg` выше 0,6; следующий бросок после расслабления ниже 0,35). Очки за бросок целые: центр до зелёного кольца — 2, до внешнего края трибла — 1, дальше — 0; максимум 10 за секцию. Зоны подчёркнуты кольцами на настоящих проволоках мишени (зелёное, оранжевое, красное), мишень не закрашивается; сцена — паб (дерево, тёплый свет), цифр на мишени нет | Зоны 2 / 1,5 / 1 / 0,5 / 0 (дробные очки противоречат решению 28); закрашивать зоны поверх мишени; мишень-кольца как в стрельбе (виртуальная тренировка должна выглядеть как реальный дартс) | Владелец: игрок сначала пробует в виртуальной, потом бросает настоящий дротик. Радиусы зон, размах разброса (0,30…0,035 м), пороги руки — в `DartsTuning`, методики очков для дартса пока нет |

## Открытые вопросы

- Начислять ли очки за сам факт прохождения секции; как считать команду неполного состава.
- Нужен ли исход дуэли или дуэль — только единица расписания.
- Нужны ли в первой версии трансляция и бегущая строка (оверлей OBS — решение 26).
